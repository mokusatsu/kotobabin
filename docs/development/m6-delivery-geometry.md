# 配送経路の描画検証

指定1180×720の実E2E画像で、出荷済み車両が道路の内側の草地を横切ることが観察された。画像だけの判断にせず、本番ビルドを実Chromium/WebKitで起動し、1語完成→Spaceでまとめ便出荷→次語の1打を入力した後、車両のDOM矩形とSVG道路の`getScreenCTM()`を同じアニメーションフレームで記録した。

最初の180ms間隔の観測は両ブラウザーで通ったが、160msのCSS補間を取り逃がしていた。観測間隔を実`requestAnimationFrame`へ変更した`e417b0b`の[CI 43508227946](https://github.com/mokusatsu/kotobabin/actions/runs/43508227946)では、Chromium job132171356088が失敗した。135フレーム中の最長道路距離は145.77px。WebKitは同じ試験に成功したため、全環境の恒常的不一致とはしない。

最悪の実測フレームではbatch1が`arrived`・残量0、指定位置は`left:88%; top:37%`だったが、描画中の位置は`left:802.375px; top:284.609px`。車両の原画基準点(128,160)/256×192から求めた画面アンカーは(802.38,329.41)、道路の最近点は(854.75,193.38)だった。SVGとDOMの場面領域はどちらも1180×640.8125、原点(0,56)で一致していた。

原因は、街の実輸送更新で経路進捗が大きく変わると、`left`と`top`を独立に補間するCSS transitionがBezier曲線の弦を通ること。道路と進捗の制御点そのものは同じだった。

修正は描画専用の進捗を160msで補間し、毎フレーム同じBezier曲線へ写す。得点・輸送量・到着・事実イベント・保存は変更しない。車種の前後も実際の描画地点の接線に合わせる。通常の入力停止中も街の確定輸送に追従し、動きを減らす設定では従来どおり途中の静止位置から確定到着位置へ即時更新する。車両DOMは保ち、場面のdetach/attachで予約RAFと描画Mapを解放する。同期レイアウト読み出しは追加しない。

検査は道路から48pxを超える明らかな路外を失敗させる回帰検査であり、46単位の道路の縁や画像の細かな足元を最終検収した証拠ではない。元原画アンカーと7pxずつの描画レーンの余裕を含む。実機iPad・物理表示遅延の受入とは区別する。修正後の実CI結果は確定後に追記する。
