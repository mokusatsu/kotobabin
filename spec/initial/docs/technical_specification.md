# ことば便 技術仕様書

版4.1　2026年11月13日

## 1 目的と適用範囲

本書は、日本語タイピングゲーム「ことば便」をWebブラウザーで実装するための技術契約を定める。入力判定、IME中断、時間計測、状態遷移、出題、記録、実績の確定と保存、街の物流・建築・設備・放置計算、描画、受入試験を対象とする。操作と記録が安定して成立し、演出や保存の成否で得点が変わらないことを実装の基本とする。

ゲームの目的、配達を選ぶ体験、導入、結果画面、実績一覧と報酬の内容は「[ことば便 ゲーム体験仕様書](game_experience.md)」に定める。本書には実装と試験に必要な共通ルールを再掲し、ローマ字受理表やブラウザー固有の処理を集約する。体験上の条件を変更する時は、対応するイベント、データ、試験期待値も同じ版で更新する。

対象はPCの物理キーボードを用いる一人用の静的Webアプリケーションである。JIS配列とUS配列で、半角ローマ字を受け付ける。仮名直接入力、IMEによる漢字変換、ソフトウェアキーボードでの本編、対人戦、アカウント同期は初版に含めない。

本書の性能、サイズ、演出時間、閾値は設計値であり、実機測定済みの値ではない。対応環境の表も、動作保証を取得済みであることを示すものではない。

画面ごとの配置、表示文、操作状態は[画面設計書](screen_design.md)、全960件の題材は[出題資材一覧](content_catalog.md)、文書の変更と確認の経緯は[レビュー履歴](review_history.md)を参照する。

## 2 構成と責務

実装はTypeScript、HTML、CSSによる静的アプリケーションとする。日本語とローマ字ガイド、操作部品はDOMで描画し、装飾の街や荷物だけをSVGまたはCanvasで描画する。テキストを画像へ焼き込まず、拡大、フォント変更、コントラスト調整に対応できるようにする。

ゲームの状態は描画と分離し、入力イベントから状態更新と演出イベントを一度だけ生成する。演出の終了コールバックで得点を加算しない。通信、音声、保存の成否によって、受理するローマ字や得点が変わらない構成とする。

| 構成要素 | 責務 | 境界 |
| --- | --- | --- |
| InputAdapter | キー、IME、長押し、フォーカスを分類 | 採点規則を持たない |
| RomajiEngine | 読みのグラフ生成、候補状態、基準長、ガイド | 画面、音声、時計を参照しない |
| GameSession | 状態遷移、荷物、得点、誤打、終了 | 時計値と正規化済みイベントを受ける |
| CourseGenerator | seedと題材から出題順を生成 | 得点、配達、誤打による分岐をしない |
| View と Feedback | 状態を表示し、演出と音を再生 | 採点や入力進行を確定しない |
| AchievementEngine | 確定事実を全72定義へ適用し、進捗・解除・報酬を求める | 打鍵の仮状態、通知の閲覧、保存再試行を条件にしない |
| CityEconomy | 確定した完成・配達から資材を作り、輸送・建築・収益・購入を計算 | 入力判定と得点を変更しない |
| WorldClock | 街の経過時間、保存済み基準時刻、最大8時間の復帰計算 | 90秒のゲーム時計と独立 |
| ProfileRepository | 設定・記録・実績・街の保存、版管理、失敗通知 | IndexedDBとメモリー実装を同じ契約で使う |
| NotificationPresenter | 解除と仮達成を区別して表示し、未読を管理する | 解除条件と得点を更新しない |

初版はゲーム中に外部APIを呼ばない。最初の読み込みで問題集と必要な素材を取得し、その後の回線断でも開いたページ内で遊べるようにする。オフラインで新しくページを開くことまでは保証しない。第三者広告、解析SDK、入力文字のサーバー送信を初版に含めない。

## 3 採点と記録の共通契約

本編の有効プレイ時間は90秒である。TUTORIALとPRACTICEは時間無制限とし、本編とは独立したセッションモードを持つ。採点、入力状態、荷物状態を単一のGameSessionで更新し、表示や音声は結果を受け取る。

### 3.1 完成と配達

語を完成させると完成点を確定する。語の途中でミスしても、最後まで打てば完成点を得られる。完成点は誤打や時間切れで減らない。

誤打せず完成した語は、おまとめボーナスの荷物に1個ずつ積む。荷物がある状態で次の語を打ち始めると、ボーナスを失う可能性と引き換えに、その語を加えた大きなボーナスを狙える。1〜4個の時は自分で配達でき、5個になった時は自動配達する。

| 状況 | 確定得点 | 荷物と入力 |
| --- | --- | --- |
| 語の完成 | 完成点を加える | 無誤打なら荷物を1個追加 |
| 語の完成直後に配達キー | 現在のボーナスを加える | 荷物を空にし、次の語はそのまま |
| 次の語の1打目 | 変化なし | 続行を選び、その語の判定を開始 |
| 誤打 | 減点なし | 荷物を空にし、その語をミスありにする。入力済み文字は残す |
| ミスありの語の完成 | 完成点を加える | 荷物に入れず、次の語は無誤打の状態で開始 |
| 5個目の完成 | 完成点とボーナスを加える | 自動配達し、次の語へ即時移行 |
| 90秒終了 | 完成済み荷物のボーナスを加える | 途中の語に完成点を与えず、結果へ移行 |

語の途中では配達できない。配達キーを押した場合は誤打にせず、「このことばを完成すると届けられます」と入力カードの外に短く示す。荷物がない時は「次のことばを完成させよう」と示す。操作キーを無反応にしない。

次の語を打ち始めるかどうかは、その語の1打目を採点対象として受けた時点で決まる。1打目が誤りでも続行を選んだ扱いとなり、保持中のボーナスを失う。次の語の日本語・読みと、成功時のボーナスを先に見せ、ガイドON時だけローマ字例も表示し、このリスクを判断できるようにする。

### 3.2 得点式

語iの基準長L(i)は、入力ルールに従うすべての有効なローマ字入力のうち、最短の打鍵数とする。完成点B(i)は10×L(i)。異なるローマ字の綴りで同じ語を完成しても、完成点と荷物の価値は同じにする。

荷物数をn、荷物になった語の完成点の合計をVとすると、おまとめボーナスPはfloor(V×n÷5)とする。nの上限は5。確定得点Sは、完成した全語の完成点合計と、実際に配達したボーナス合計を足した値とする。計算は整数で行う。

| 1語の完成点が50点の場合 | 荷物の完成点合計V | 今配達するボーナスP |
| --- | --- | --- |
| 1個 | 50 | 10 |
| 2個 | 100 | 40 |
| 3個 | 150 | 90 |
| 4個 | 200 | 160 |
| 5個 | 250 | 250 自動配達 |

例として、3語を無誤打で完成した時点では、完成点150点は確定し、90点の追加ボーナスを持っている。ここで届ければ合計240点。4語目に挑戦してミスすると90点の追加ボーナスだけが消え、確定済み150点は残る。4語目を打ち終われば、その語の完成点50点を得て合計200点になる。

### 3.3 救済と集計

1語ごとの制限時間、HP、突然のゲームオーバーは設けない。読めない・打てない時は一時停止から、その語だけを飛ばせる。スキップ時は保持ボーナスを配達してから荷物を空にし、途中の語は0点とする。スキップ操作自体は正解打鍵にも誤打にも数えず、その語で既に記録した正解打鍵と誤打は双方とも正確率に残す。スキップを使った回は救済ありの本編記録とし、通常の自己ベストと分ける。モードはMAINのままとし、PRACTICEの実績へ加算しない。必ず理由を操作前に示す。

正確率は正解として受理した実打鍵数÷（正解打鍵数＋誤打数）×100とし、小数1桁で表示する。スキップした語や時間切れの語も、それまでの正解打鍵と誤打を同じ範囲で集計し、0〜100%に収める。採点対象打鍵が0の場合は「計測なし」。基準打鍵/分は完成語の基準長合計÷有効プレイ秒数×60とし、通常の完走は90秒を使う。待ちや配達の判断時間も含み、一時停止時間だけを除く。WPMや実際の文字数と呼ばない。

## 4 ローマ字判定

### 4.1 入力方式

文字判定には、キーボードの位置ではなく入力された文字の値を使う。英字は小文字へ正規化し、ShiftやCaps Lockによる大文字を誤打にしない。読みはひらがな、長音記号「ー」だけで構成する。数字は読みへ展開し、句読点・空白は表示文だけに置いて入力対象にしない。読みに文字を足したり削ったりする曖昧な補正は行わない。

ローマ字ガイドは正解経路の一例である。別の有効な綴りが打たれたら、その入力を含む経路へ即時に切り替える。既に受理したキーは書き換えず、残りだけを更新する。候補に迷いがあっても正しいキーを誤打にしない。

### 4.2 受理表

以下を初版の完全な基本受理表とする。括弧内は同じ読みで使える別経路。語のデータにローマ字正解文字列を1本だけ持たせてはならない。

| 読みの組 | 受理するローマ字 |
| --- | --- |
| あ い う え お | a / i(yi) / u(wu,whu) / e / o |
| か き く け こ | ka(ca) / ki / ku(cu,qu) / ke / ko(co) |
| さ し す せ そ | sa / si(shi,ci) / su / se(ce) / so |
| た ち つ て と | ta / ti(chi) / tu(tsu) / te / to |
| な に ぬ ね の | na / ni / nu / ne / no |
| は ひ ふ へ ほ | ha / hi / hu(fu) / he / ho |
| ま み む め も | ma / mi / mu / me / mo |
| や ゆ よ | ya / yu / yo |
| ら り る れ ろ | ra / ri / ru / re / ro |
| わ を | wa / wo |
| が ぎ ぐ げ ご | ga / gi / gu / ge / go |
| ざ じ ず ぜ ぞ | za / zi(ji) / zu / ze / zo |
| だ ぢ づ で ど | da / di / du / de / do |
| ば び ぶ べ ぼ | ba / bi / bu / be / bo |
| ぱ ぴ ぷ ぺ ぽ | pa / pi / pu / pe / po |
| ゔ | vu |
| ぁ ぃ ぅ ぇ ぉ | xa(la) / xi(li) / xu(lu) / xe(le) / xo(lo) |
| ゃ ゅ ょ | xya(lya) / xyu(lyu) / xyo(lyo) |
| っ | xtu(ltu,xtsu,ltsu)。重ね子音は後述 |
| ー | ASCIIのハイフン - |

拗音は、き・ぎ・に・ひ・び・ぴ・み・りに小さい「ゃ・ゅ・ょ」が続く場合、k/g/n/h/b/p/m/r＋ya/yu/yoを受理する。例はkya、gyu、nyo。し＋小文字はsya/syu/syoとsha/shu/sho、ち＋小文字はtya/tyu/tyo、cya/cyu/cyo、cha/chu/cho、じ＋小文字はzya/zyu/zyo、jya/jyu/jyo、ja/ju/jo、ぢ＋小文字はdya/dyu/dyoを受理する。

外来音の短縮経路は、いぇ=ye、うぃ=wi、うぇ=we、うぉ=who、しぇ=sye/she、じぇ=zye/je/jye、ちぇ=tye/che/cye、てぃ=thi、てゅ=thu、でぃ=dhi、でゅ=dhu、ふぁ=fa、ふぃ=fi、ふぇ=fe、ふぉ=fo、ふゅ=fyu、ゔぁ=va、ゔぃ=vi、ゔぇ=ve、ゔぉ=vo、ゔゅ=vyuとする。

拗音・外来音は、基本表の大きい仮名と小さい仮名を別々に入力する経路も受理する。例えば「きゃ」はkya、kixya、kilya。「しゃ」はsha、sya、shixya、sixya、cilya等である。この合成規則で許される経路を全て受け付け、上の例だけに限定しない。ゐ・ゑ・小さいゎ・ヵ・ヶ・踊り字・絵文字は初版の読みに入れない。

### 4.3 んの確定

「ん」はnn、n'、xnを常に受理する。後続する語中の仮名経路が子音から始まり、その先頭がy以外である時はn一文字も受理する。次の仮名がな行の場合も含め、「んな」はnna、nnna、n'na、xnnaを受理する。

語末、および次に母音またはyから始まる経路が続く場合は、n一文字では確定しない。「んあ」はnna、n'a、xna、「んや」はnnya、n'ya、xnyaとなる。「かん」はkann、kan'、kaxnを受理し、kanだけでは完了にしない。語末を1打で終わらせないことで、nnの2打目が次の語へ流れる問題を避ける。

「んな」のnn入力時は、最初のnで「ん」を確定して次のnを「な」の途中とみなす状態と、nn全体で「ん」を確定した状態の両方を保持する。後続のaまたはnaで解決し、先に一方へ固定してはならない。

### 4.4 っの確定

小さい「っ」は、明示入力xtu/xtsu/ltu/ltsuの後に次の仮名を打つ経路を受理する。次の仮名経路がa/i/u/e/o/n以外から始まる時は、その先頭子音を1回余分に打つ経路も受理する。例はがっこう=gakkou、まっちゃ=maccha、きって=kitte。chi/cha/chu/cho/cheの前ではtを置く慣用経路も受理し、matchaも正解とする。

連続する「っ」や、語末の「っ」は明示入力で扱えるが、初版の題材には入れない。判定できることと、初見に出すことを分ける。

### 4.5 判定エンジン

読みの位置を節点とし、受理表・合成規則で許される文字列を辺に持つ非決定性の状態機械を構築する。読みを先に最長一致で一意に区切らない。「きゃ」をまとめて打つ経路と分けて打つ経路、「んな」の曖昧な途中状態を共存させる。

各打鍵で全ての生きた候補から遷移を求め、遷移先が1つでもあれば正解とする。遷移先が0なら誤打とし、状態は直前のまま。読み末尾へ到達したら完成候補を返し、対応する入力操作が確認された時だけGameSessionが完成事実を1回発行する。単語を跨いで入力を持ち越さず、同じキーイベントを次の語に再利用しない。基準長はこの同じグラフで最短経路を計算して求める。

## 5 キーボード入力と処理順

入力は入力カードにフォーカスがある時だけ捕捉する。ゲーム対象の英字、ASCIIアポストロフィ、ASCIIハイフンは、正解経路に遷移がなければ誤打として1回数える。数字や未対応の記号、修飾キー単独、Backspace、Deleteは採点せず、必要時に操作案内を出す。ブラウザーのショートカットとTab移動を妨げない。

| 操作 | 動作 |
| --- | --- |
| 英字と入力対象記号 | 読みを1打進めるか、誤打を1回記録 |
| Space | 語の境目で配達。標準設定 |
| Enter | 設定でSpaceの代わり、または追加の配達キーにできる |
| Esc または画面の一時停止 | 状態を保ったまま停止 |
| Tab | 通常のフォーカス移動。入力カードを離れたら停止 |
| Backspace Delete | 訂正不要の案内。文字は戻さず、誤打にも数えない |
| Ctrl Alt Metaとの組合せ | ゲーム入力にせずブラウザーへ渡す |
| 長押しの自動反復 | 文字・配達・メニュー決定を発生させない |

配達キー設定はSpace/Enterのいずれか一方、または両方を選べる。変更は一時停止中またはホームで行い、説明と画面上のキー表示を同時に更新する。読みの入力文字そのものは割り当て変更しない。

### 5.1 入力の準備

初回、再挑戦、練習開始で入力の準備状態へ入る時は、入力カード内のinput要素へフォーカスを移し、その成功を確認してから入力受付を有効にする。開始操作のクリックやキーイベントを文字入力へ再利用しない。フォーカスを確保できなければ時間を開始せず、入力カードを選ぶ案内を示す。

本編のREADYでは最初の語を表示してもタイマーを進めない。英字、ASCIIアポストロフィ、ASCIIハイフンの最初の採点対象キーで時間を開始し、そのキーを1打目として判定する。誤った1打目も開始と誤打として扱う。Spaceなどの操作キーで時間を開始しない。

### 5.2 イベント処理の順序

キーの文字値にはKeyboardEvent.keyを用い、codeを文字と同一視しない。MDNはkeyの決定に`the keyboard locale and layout`が関係すると説明している。codeを使う場合も同一物理操作の関連付けだけに限定し、入力文字の判定には使わない。[技1]

1. フォーカス、ゲーム状態、修飾キー、長押し、IME関連を分類する。
2. PLAYINGでは操作キーも含めてハンドラー開始時刻を記録し、90,000ms以上なら新規採点より終了を優先する。
3. READYで最初の採点対象文字を受けたら、開始時刻と操作IDを仮に作る。キーを小文字化し、RomajiEngineから文字表示の候補を求める。
4. 非合成の半角入力として同一操作を確認できた時だけ、その操作をGameSessionへ確定する。IME関連・貼り付け等であれば仮反映を取り消す。
5. 正解または誤打を1回確定し、語が完成したら完成点、荷物、必要な自動配達、次語への移行を順に確定する。
6. その更新で生じた語完成・配達などを、一意の連番を持つ確定事実としてAchievementEngineへ渡す。
7. メモリー上の最新状態を表示し、実績進捗の保存を非同期で依頼する。演出、音声、データベースの完了を次の打鍵の条件にしない。

Space等の既定動作を抑止するのは、入力要素でゲーム操作として処理する場合だけとする。通常の半角文字は確認用のネイティブinputを受け取れるようにし、inputの内容を別途もう一度採点しない。操作キーによる配達は、直前までの未確定操作との順序を保って処理する。IMEを確定・終了するためのEnterを配達へ転用しない。設定画面や通常のボタン操作にはゲーム用の捕捉を適用しない。

入力確認で採点可能なイベント列を取得できない環境は、READYへ移さず入力再確認の案内を出す。対象環境で通常入力がこの確認により待たされないことを第15節の実機試験で確かめる。

## 6 IMEと入力環境の確認

ブラウザーからOSのIME状態を常に確実に取得・変更できるという前提は置かない。実入力を受け取るinput要素を入力カード内に置き、入力確認とイベントによる検知で対応する。見た目のローマ字ガイドは別DOMで描き、入力要素にはラベル、フォーカス表示、読み上げ用の説明を持たせる。

compositionstart、isComposing、互換補助としてkeyCode=229、keyがProcessである場合をIME関連の候補とする。keyCodeは通常の文字判定には使わない。MDNは`isComposing is false even when the event is part of composition`と説明しており、isComposingだけに依存しない。[技2]

### 6.1 仮入力と確定事実

InputAdapterはkeydown、beforeinput、input、keyup、composition関連イベントを操作IDへ関連付ける。keydownから次の文字表示を仮に更新しても、語完成、得点、荷物、実績進捗を永続化する事実はまだ発行しない。判定済みの操作IDをinput側でもう一度採点しない。

通常の文字操作は、対象のkeydownと対応するネイティブinputが、単一の半角英字・アポストロフィ・ハイフンを示し、正規化後のkeyと一致し、合成・貼り付け・ドラッグ・音声入力のいずれでもないことを確認して確定する。プログラム生成のイベントとvalueへの代入は確認にならない。MDNのinput説明は`as a direct result of a user action`である。[技8]

InputEvent.isComposingが示す範囲は`after compositionstart and before compositionend`であり、合成境界をそれだけで判断しない。inputType、操作中に観測したcompositionイベント、キーの互換情報、対応する入力内容を合わせて確認する。[技9]

IME関連を検知したら同一操作の仮反映だけを破棄し、確定済みの直前状態から表示を復元して停止する。同じ操作の下流に未確定入力があれば、その順序とIME所属を再分類する。別の操作として既に確定した語、得点、荷物、実績を巻き戻さない。AchievementEngineへ渡した事実を後からIME取消しで取り消す設計にはしない。

ブラウザー間でkeydown、composition、input、keyupの厳密な共通順序が保証されるとは扱わない。対応関係を特定できない入力は採点せず停止し、入力再確認へ進める。各対象環境では、語の最終キー、語境界、IME開始・終了、Enterでの変換確定、急速な連続入力のイベント列を記録し、誤確定と入力欠落がないことを確認する。

### 6.2 半角入力の確認と復帰

最初の入力確認では半角aを1回打てることを確認する。この操作を得点、正確率、語の完成、配達、実績へ計上しない。IME関連のキー操作が終わり、半角aを確認できた後も、本編は明示的な「再開」とフォーカス確認を経て復帰する。

進行中の入力確認では元のモード、入力候補、現在語、荷物、得点、有効経過時間を保持する。新しいGameSessionを作り直さない。READYからの確認では最初の採点対象文字を確定するまで時計を動かさない。入力準備に失敗した操作は90秒の開始にも使わない。

時間切れと入力確認が重なる場合、判定期限にはkeydownハンドラー開始時刻を使う。期限内に受け付けた最後の操作の分類を解決してからRoundFinishedを発行する。確認済みなら期限内の操作として1回計上し、IME等なら計上しない。以後の入力を追加せず、待っている間にプレイ時間を延長しない。キーアップやフォーカス離脱で対応inputを確認できなかった操作は未確定のまま採点しない。

貼り付け、ドラッグ挿入、音声入力、変換確定文字を打鍵へ変換しない。半角入力が正しく届く対応環境で、通常の確定が描画・演出待ちによって遅れないことを公開条件とする。

## 7 時計と一時停止

残り時間はperformance.nowを用いた単調時間の差から計算し、描画フレーム数やsetIntervalの呼び出し回数から減らさない。タイマーAPIについてHTML Standardは`does not guarantee that timers will run exactly on schedule`と明記している。[技3]

採点の期限はkeydownハンドラーの処理開始時刻で定義する。これは物理キーが押された厳密な時刻と同義ではない。先に有効経過時間を計算し、90,000ms未満なら受理、90,000ms以上ならそのキーを採点する前に終了処理を行う。描画が遅れていても期限後の入力を採点しない。この境界を単体試験で再現できるよう、GameSessionへ時計を注入する。

一時停止では経過時間を固定し、再開時に新たな開始基準を設定する。停止イベントの処理開始時点で既に期限に達している場合は終了を優先する。再開のために押したキーを読みの入力として再利用しない。長い処理停止や端末スリープのあとに状態が不連続になった場合は、記録を勝手に補正せず停止画面を出す。

### 7.1 フォーカスと非表示

フォーカス喪失と文書の非表示を別々に監視する。MDNはblurについて`does not tell you that your page is actually hidden`と説明している。window.blur、入力要素のblur、visibilitychangeをそれぞれ停止の契機にし、重複しても停止時刻を二重加算しない。[技4]

### 7.2 停止と終了の手続き

Esc、停止ボタン、入力カードからのフォーカス離脱、タブ非表示、IME変換開始で一時停止する。停止している間は本編の90秒時計、入力、得点、保持中のボーナス荷物、入力演出を進めない。街の輸送・営業収益は第16章の実経過時間で進み、一時停止による新しい資材は生まれない。戻っただけで再開せず、再開ボタンで入力要素へフォーカスを戻し、フォーカスが戻ったことを確認してから入力とタイマーを再開する。再開操作のイベントは採点しない。フォーカスが戻らなければ停止を維持する。停止画面では問題を隠し、再開前の準備表示で元の途中状態を確認できる。

途中終了は「続ける」を初期選択とする確認画面を経て行い、完走記録や自己ベストに入れない。更新・タブを閉じる操作に対する中断再開の保存は初版に含めない。終了タイマーと最後の入力、最後の配達が重なっても、結果を確定する処理は1回だけ実行する。

90秒終了後は完成済みの荷物を自動配達し、通常の配達と区別して「最後の荷物を届けました」と示す。未完成語の入力はここで打ち切り、その語にも誤打がある場合は復習候補に含める。結果の表示や祝福の演出を待たず、再挑戦操作を受け付ける。再挑戦で同じ問題列を準備するUIの待ち時間は300ms以下を目標とする。

## 8 状態遷移

| 状態 | 受け付ける主操作 | 次の状態 |
| --- | --- | --- |
| HOME | コース、届け先、開発計画、設備、練習、設定 | 入力確認が必要ならINPUT_CHECK、確認済みならTUTORIAL/READY/PRACTICE |
| INPUT_CHECK | 半角aの確認、戻る | 開始時は保持したTUTORIAL/READY/PRACTICE、再確認時はPAUSED |
| TUTORIAL | 本編と同じ打鍵・配達、スキップ、停止、練習へ | READY、PAUSED、PRACTICE |
| READY | 最初の採点対象キー、停止、IME再確認 | PLAYING または PAUSED |
| PLAYING | 読みの入力、語境界の配達、停止 | PLAYING、PAUSED、RESULT |
| PAUSED | 再開、入力再確認、スキップ、途中終了 | 元のREADY/PLAYING/TUTORIAL/PRACTICE、INPUT_CHECK、HOME |
| RESULT | 同じ順で再挑戦、新しい順、復習、コース選択 | READY、PRACTICE、HOME |
| PRACTICE | 入力、配達、次の語、停止、本編で試す、終了 | PRACTICE、PAUSED、READY、INPUT_CHECK、HOME |

ホームで選んだ開始先をlaunchTargetとしてTUTORIAL/READY/PRACTICEのいずれかに確定し、入力確認を挟んでも保持する。練習を選んだ場合はPRACTICEへ進む。初回の「遊ぶ」はTUTORIAL、その後の本編はREADYへ進む。設定、手帳、図鑑、街の詳細、設備、研究、確認ダイアログは進行状態とは別の画面状態として扱う。街の投資操作はHOME/RESULTに限定する。MAINのREADY、PLAYING、PAUSED中は購入・届け先変更・新しい街への移行を認めない。練習中に設備へ進む場合も練習を終了してからHOMEへ戻る。HOMEとRESULTから手帳を開いた場合は元画面へ戻る。PLAYINGから手帳へ進む場合は先にPAUSEDへ移し、閉じてもPAUSEDを維持する。図鑑から練習を選ぶ操作は新しいPRACTICEの開始として扱う。

停止中のセッションを保持したまま手帳や図鑑から別の練習・本編を開始する場合は、途中終了確認を通す。取り消しでは元のPAUSEDを維持する。確定した場合は旧セッションの確定事実を保持し、MAINなら途中終了のRoundFinished、PRACTICEならPracticeSessionEndedを1回発行してから、新しいセッションを生成する。途中終了では未配達ボーナスを追加確定せず、便・通常の実績を解除しない。既存セッションを無言で上書きしない。

PRACTICEの「本編で試す」はPracticeSessionEndedを1回発行し、確定済みの練習成果を保持したまま、第9.2節の出題計画で新しいMAINのREADYへ進む。必要な入力確認を挟む場合も開始先READYを保持する。F06の資格は第11.4節のとおりREADYで固定する。

一時停止と入力再確認では元のモードとセッションを保持する。INPUT_CHECKからの復帰で新しいゲームを作り直さない。READY、TUTORIAL、PRACTICEの停止復帰にも同じ入力保護を適用する。READYで停止した場合はREADYへ戻し、入力フォーカスを確認しても時計は開始せず、最初の採点対象キーまで残り90秒を維持する。入力確認の「戻る」は、開始時ならHOME、再確認時なら元のPAUSEDへ戻す。

PLAYING内には「語の境目」と「入力中」の状態を持つ。語の境目で最初の採点対象キーを受けると入力中になり、語が完成すると境目へ戻る。最初の語は入力位置0で始まり、完成後の次語も同じ判定器を使う。ミスありの印は語を切り替える時だけ解除する。

90秒完走での終了は新規入力の受付を止め、最後の期限内操作を確定してから終了済みフラグを一度だけ立てる。未配達ボーナスの確定、結果の集計、RoundFinishedの発行を各1回行う。同じ最終キー、終了タイマー、配達演出の完了が重なっても同じ結果になるよう、得点更新を単一の経路に集約する。

## 9 出題と問題データ

難易度は、制限時間を短くするのではなく、語の長さと入力要素で変える。3コースを最初から選択でき、解放作業を要求しない。初期選択は「ゆったり」。コース内でプレイヤーに合わせた隠れた難易度変更は行わない。

| コース | 題材 | 基準長Lの範囲 | 主な入力要素 | 採用題材数 |
| --- | --- | --- | --- | --- |
| ゆったり | 身近な短い語 | 3〜8 | 清音、濁音、半濁音。複雑な連続は避ける | 240 |
| ふつう | 日常語と短い句 | 5〜14 | ん、っ、拗音、長音を追加 | 300 |
| 挑戦 | 読みやすい短文 | 10〜24 | 複数の入力要素、外来語を組み合わせる | 420 |

各コースの問題順は固定の出題パターンを使う。パターンは「易・中・中・難・易」の5語周期とし、そのコースの範囲内で難しさに山と休息を作る。サブ区分は基準長と特殊入力の数を用い、第9.3節の固定手順で生成する。語彙の難しさや常識問題でタイピング能力以外を試さない。

新しい問題を選んだ時に乱数seedと出題順を作り、再挑戦では同じ順を再利用する。出題決定を配達回数、誤打、点数に依存させない。各小区分をseed付きでシャッフルした袋から選び、袋の中を使い切るまで重複させない。袋を補充する時も直前と同じ語は避ける。配列や乱数処理の版を記録する。

題材は960件を編集確認し、初期試作ではそのうち30件で遊びを検証する。旧240件のID・表示・読み・主コース・主分類・基準長は維持する。表示文、読み、基準長、難しさ、特殊入力タグ、公開可否を全件確認する。読みに対応しない漢字、複数の読みが競合する文、難読固有名詞、版権のある歌詞や台詞、罵倒・差別表現を避ける。助詞「は」「へ」は表示した読みどおりにha/heで打つ。

完成した960件の正本は[data/words.json](../data/words.json)とする。人が閲覧する一覧は[出題資材一覧](content_catalog.md)、機械的な構造は[data/words.schema.json](../data/words.schema.json)、入力規則は[data/romaji_rules_v1.json](../data/romaji_rules_v1.json)に定める。文書版4.0と以下のデータ版は別々に管理する。

| 正本の項目 | 固定値または意味 |
| --- | --- |
| schemaVersion | `2.0.0`。出題ファイルの構造版 |
| contentVersion | `2.0.0` |
| inputRuleVersion | `romaji-1.0.0` |
| dictionarySetId | `kotobabin-ja-960-v2`。現在採用している全体集合 |
| collectionSets | 旧240件、全960件、3コース別の固定ID集合 |
| words | 完成した960件の問題データ |
| prototypeIds | 同じ960件から参照する試作30件の問題ID。各コース10件 |
| tutorialIds | 同じ960件から参照する操作体験用の問題ID |

入力規則ファイルは`schemaVersion=1.0.0`、`inputRuleVersion=romaji-1.0.0`を維持する。出題ファイルの構造版と入力規則の構造版を同一値とみなさない。正本には選定方針と編集状態の説明も含める。各項目の型、必須性、追加項目の制約はスキーマを参照する。

### 9.2 図鑑と練習からの本編

現在の全960語と初版240語を別の固定集合として持つ。主分類はくらし、食べもの、生きもの、まちと道具、自然と季節、人とことばの6種で各160語とする。主コースは1語につき1つとし、全体240・300・420語、各分類40・50・70語の内訳を[ゲーム体験仕様書](game_experience.md)と照合する。同じ表記の語を別IDで収集へ重複加算しない。導入の短語も同じ問題IDを参照する。

試作30語は正本の`prototypeIds`、操作体験の短語は`tutorialIds`で指定する。両方とも`words`に含まれる同じ問題IDを参照し、別の表示文、読み、基準長を複製して持たない。

図鑑は960語を最初から検索・選択可能とし、未完成、練習中、練習で無誤打3回達成済みを進捗データから抽出する。閲覧や選択だけでは収集を加算しない。無誤打3回の語別資格は、同じ語のPRACTICEでの確定完成を累積して求める。復習もPRACTICEの一種であり、同じ資格へ加算する。

「このことばを含む本編」は、選んだ語の主コースを使い、最初の5語のうち、その語のdifficultyBandに対応する位置を開始前に確定する。易なら1番または5番、中なら2番または3番、難なら4番に置く。複数位置があればseedから決定する。残りを通常の袋方式で生成し、指定語は同じ袋から取り除いて直後に重複させない。易・中・中・難・易の波を維持する。

出題計画はgeneratorVersion、seed、courseId、contentVersion、preferredWordIdの組から決める。通常出題のpreferredWordIdはnullとする。最初の5語と以後の生成規則を開始前に固定し、進行中の誤打・得点・配達で変更しない。再挑戦は同じ出題計画を使い、前回到達した語より先も同じ規則で生成する。保存には出題計画IDと実際の問題ID列を残す。

図鑑と練習は集合フィルター「すべて」「初版240語」「ゆったり」「ふつう」「挑戦」と状態フィルター「未完成」を組み合わせられる。検索結果を先頭から順に練習し、完成したら次の未完成語へ進める。E04のために通常出題の偶然を待たせない。将来の追加語でも以下の集合を拡張せず、新しい集合IDを作る。

| collectionSetsのキー | 必要ID数 | 用途 |
| --- | --- | --- |
| `kotobabin-ja-240-v1` | 240 | E04、初版図鑑の達成表示 |
| `kotobabin-ja-960-v2` | 960 | L01・L02の300/480語、L03の全960語 |
| `kotobabin-ja-relaxed-v2` | 240 | L04 |
| `kotobabin-ja-standard-v2` | 300 | L05 |
| `kotobabin-ja-challenge-v2` | 420 | L06 |

旧集合は[旧240語の固定参照](../data/legacy_word_index_v1.json)とも照合する。E01・E02・E03の10/50/150語とE05の各分類5語は、現在採用している960語の確定完成を対象にする。既存の解除と語別完成履歴を維持する。

### 9.3 難度帯の固定生成

難度帯は各コースの内部で生成する。基準長をLとし、読みの「ん」「っ」「ー」の文字数、基本拗音ペア数、外来音ペア数から次の整数を求める。

```text
complexityScore = L + んの数 + 2×促音数 + 2×基本拗音ペア数 + 2×外来音ペア数 + ーの数
```

基本拗音ペアは第4.2節の拗音の組、外来音ペアは同節の外来音短縮経路の組を数える。同じ仮名の組を両方に重複計上せず、選んだローマ字の綴りによって数を変えない。

各コースを`(complexityScore, canonicalLength, id)`の昇順で並べ、下位40%を`easy`、次の40%を`medium`、残り20%を`hard`に固定する。IDは文字列の昇順で比較し、同点でも境界を一意に決める。所属は1語につき1帯だけとする。

| コース | 総数 | easy（易） | medium（中） | hard（難） |
| --- | --- | --- | --- | --- |
| relaxed | 240 | 96 | 96 | 48 |
| standard | 300 | 120 | 120 | 60 |
| challenge | 420 | 168 | 168 | 84 |

この帯は、同じコース内の長さと入力要素による編集上の相対区分である。体験で実測した難易度や、特定のプレイヤーの入力速度を保証するものではない。進行中の成績に応じて帯を変えず、第9章の「易・中・中・難・易」の波と、第9.2節の対象語の配置に同じ帯を使う。

### 9.4 基準長と資材の再検査

基準長は単一の正解綴りから求めず、[入力規則JSON](../data/romaji_rules_v1.json)に定義された第4章の全受理経路から入力グラフを構成し、読み終端までの最短打鍵数として生成する。基本表、拗音・外来音の短縮と分割、「ん」の確定、「っ」の明示入力と重ね子音を同じ計算に含める。保存済みの`canonicalLength`を手入力で修正して正本とすることはできない。

出題資材は[tools/validate_content.py](../tools/validate_content.py)で再検査できる。件数、ID、分類、文字種と文字数、基準長、タグ、complexityScore、難度帯、`prototypeIds`と`tutorialIds`の参照整合を、正本と規則JSONから確認する。修正時は生成値を再計算し、関連する版と一覧をそろえる。

この検査は出題資材と入力規則の整合確認である。第15章のゲーム本体の受入試験、物理キーボードとIMEを用いた実機試験、第17章の公開条件を置き換えない。

## 10 実行中データと永続化

実行中には、確定状態と未確定の入力操作を分けて持つ。確定状態は出題位置、入力候補、現在語の受理打鍵、誤打フラグ、得点、荷物の問題IDと完成点、正解数・誤打数・配達数、有効経過時間、実績用の便内統計を含む。問題集・出題計画・入力規則・得点規則・実績定義・届け先・資材倍率は開始時に固定し、途中で差し替えない。

音量、文字サイズ、動きの軽減、配達キー、ガイド、実績通知は停止中の操作で変更できる。ガイドを一度でも表示した履歴は、その便が終わるまで残す。称号や額縁、通知の好みは得点・出題・実績の適格性に影響しない。H05だけはガイド表示履歴を条件に使う。

### 10.1 保存単位

設定、結果、実績、報酬、街、経済イベントは同じoriginのIndexedDBへ保存する。実績進捗、解除記録、報酬の所有権、処理済み事実の位置を同一readwriteトランザクションで更新する。W3C勧告は変更について`either all of the changes must be written`と定める。個別requestのsuccessだけで保存済みと表示せず、transactionのcompleteで成功を確認する。[技7]

| 保存対象 | 主な内容 |
| --- | --- |
| profile | 設定、手帳の目標1件、装着中の称号・額縁、通知設定、カタログ開始情報 |
| results | 直近30便、自己記録、出題計画IDと問題ID列、各規則版、ガイド・救済区分 |
| achievementProgress | 累積語数、発送荷物数、異なる語ID、語別練習成功回数、便内最大の自己最長、コース別成立記録 |
| unlocks | 実績IDごとの解除日時、成立条件の版、根拠事実、対象モード。1実績につき1件 |
| rewards | 切手、称号、絵葉書、台紙、街の節目の所有権。報酬キーごとに1件 |
| readState | 未読の実績・報酬と、既読にした状態。解除状態から独立 |
| factCursors | セッションIDごとの適用済み連番。結果再表示や再試行で二重加算しない |
| city | 現在のcityId、資源、地区、計画、設備、輸送待ち、世界時計の基準、経済版、状態revision |
| economyProfile | 設計図、研究、累積到着資材、再出発回数、過去都市の要約 |

| metadata | 保存形式の版、旧版移行済み状態、記録削除の世代、操作タブのowner/epoch |

確定事実の識別子はsessionIdと単調増加のfactSequenceで構成する。再送には同じ識別子を使い、適用済みのものを加算しない。複数タブでは第16.8節の所有権を持つ1タブだけがプレイと街を更新する。同じストアを対象にしたトランザクション内で最新状態を読み、事実を適用する。古いメモリースナップショットをそのまま全体上書きしない。

トランザクション中に描画、外部通信、音声、ユーザー入力を待たない。事実の適用と必要なストア書き込みだけをまとめる。実績の計測は確定した語・配達・便終了時に行い、各打鍵で全履歴を読み直さない。全打鍵ログの永久保存は不要とし、進捗の集計値、解除根拠、処理済み位置を保持する。

### 10.2 保存できない場合

保存の要求と、今回のプレイ内での解除は分ける。保存中は未確認、transactionのcomplete後は保存済み、失敗時は今回のみとする。保存できなくてもメモリー上でプレイ、実績の計測、報酬表示を続けるが、永続したと表示しない。

開始時に保存できなければ「この回の街と切手は、ページを閉じると残りません」を開始前と手帳に示す。途中の保存失敗でも同じ状態を明示し、今回のみの進捗と以前の保存済み進捗を区別する。結果のテキストをコピー可能にする。保存の再試行が成功した時だけ未保存の確定事実を反映して表示を更新し、同じ解除を再通知しない。

ページの更新やタブを閉じる操作に対する本編途中再開は初版に含めない。通常の途中終了操作では、その前に成立済みの全・練の確定事実を保存対象へ出す。書き込み失敗を隠して「残ります」と保証しない。

### 10.3 実績導入前のlocalStorage版と記録削除

本節の移行元は実績導入前のlocalStorage版である。実績・図鑑・練習資格を保持する旧IDB版の移行は第16.8節に従う。旧版localStorageの設定、チュートリアル完了、自己記録は取り込み、移行完了後も表示できるようにする。localStorageの取得自体が失敗する場合や、書き込みが`Throws a QuotaExceededError if the new value couldn't be set`となる条件もあるため、旧データへのアクセス失敗を本編停止へつなげない。[技6]

実績導入前のlocalStorage版には完全な実績事実がないため、過去結果の語数・得点から累積、図鑑、練習資格、実績の成長比較を遡及生成しない。実績カタログ開始後の確定事実だけで計測する。旧自己記録は旧記録として残し、実績比較用の記録集合へ混ぜない。移行途中の失敗で旧データを先に削除せず、再試行で設定や結果を二重取り込みしない。

削除は自己記録、街・実績・収集、設定を別操作にする。自己記録の削除は実績用の成長比較履歴も消すが、解除済みの切手と報酬は残す。「街・実績・収集を削除」は、実績進捗、解除、切手、称号、図鑑の完成履歴、練習資格、装飾報酬、街の資源・設備・計画、設計図、研究、経済累積を消し、計測開始点と初期の街を作り直す。新しい街への再出発とは別操作であり、再出発では実績等を保持する。自己記録の表示は残すが、削除前の結果を新しい実績へ遡及適用しない。設定のリセットでは記録を消さない。

削除対象を確認画面に明示し、削除世代を更新して、旧世代の非同期書き込みが消した記録を復活させない。旧版の取り込み済み印は維持する。他サイトや無関係なキー、データベースを削除しない。

### 10.4 自己記録と復習

自己記録の比較キーは、コース、出題計画ID、題材版、出題生成版、入力規則版、得点規則版、ガイド使用区分、通常か救済ありかとする。同じseedでも対象語を含むかどうかが違えば、別の出題計画として比較する。任意ヘルプを含め、一度でもガイドを表示した便は「ガイド表示あり」とし、後でOFFに戻しても区分を戻さない。

同じ条件と同じ順序の自己記録を主要な比較とし、別の並びの最高点は参考記録にする。直近30便を超えた詳細結果は保持しなくてよいが、比較キーごとの最高得点・最高基準速度と、実績比較に必要な完成語数等の適格情報は集計値として保持する。実績解除済みの状態は結果の保持件数に依存させない。

復習はその便に誤打した語を重複除去し、誤打数の多い順・同数は出題順で最大10語選ぶ。未完成語も誤打があれば候補に含める。誤打がない場合は復習ボタンを表示せず、図鑑から練習へ進める。復習と図鑑練習は同じPRACTICE処理を使い、時間無制限で終了できる。

## 11 実績イベントと解除の確定

全72件の名称、閾値、報酬、対象は[ゲーム体験仕様書第7節](game_experience.md#7-実績全72件)を正とする。本書では同じ実績IDを使い、全一覧を複製せずに計測の契約を定める。目標の固定、手帳の閲覧、隠し条件の公開、通知の表示は、計測を開始する条件にしない。

### 11.1 確定事実

| 事実 | 必須の内容 | 実績に使う意味 |

| DeliveryCommitted | 理由、荷物数、ボーナス、直前に完成した語位置 | 手動配達、満載、順序・複合条件、発送荷物数 |

タイピングの各事実はsessionId、factSequence、モード、規則版、確定時刻を持つ。街の事実はcityId、economyEventId、経済版、確定時刻を持ち、タイピングのモードを偽装しない。日時は履歴の表示だけに使い、日付、連続日数、特定時刻を解除条件にしない。TUTORIALの短語もWordCompletedを使い、入力確認用aは事実を発行しない。

DeliveryCommitted.reasonはmanual、full、deadline、skipの4種とする。実績の配達回数はmanualとfullだけを各1回として数える。G04・G05は同じ2種のcargoCountを加算し、1個配達なら1、満載なら5を加える。deadlineとskipは得点・追加資材用の事実として残すが、配達回数にも発送荷物数にも加えない。

### 11.2 モードと確定時点

| 表示上の対象 | 技術上の適格性 | 確定時点 |
| --- | --- | --- |
| 全 | TUTORIAL、PRACTICE、MAIN。MAINの救済使用を含む | 確定した語・配達ごと。途中終了後も保持 |
| 練 | PRACTICE。図鑑練習と復習を区別せず含む | 確定した練習成果ごと。途中終了後も保持 |
| 便 | MAIN、90秒完走、完成語数1以上。救済ありを含む | RoundFinishedで確定 |
| 通常 | MAIN、90秒完走、スキップ数0 | 同じ便のRoundFinishedで確定 |
| 街 | 到着、建築、開通、有料購入、連携、研究、再出発 | 経済トランザクション成立時。放置中の到着と建築も含む |

全・練の進捗をRoundFinishedでもう一度加算しない。通常の便内統計は打鍵や配達で更新するが、解除と通常の累積成立記録は完走時だけ確定する。途中終了した便からB系統、C系統等の解除を出さない。途中でスキップしても、その前後の全・練に該当する事実を取り消さない。

連続成功はcurrentCleanStreak、maxCleanStreakInSession、bestCleanStreakHistoryを分ける。誤打した時に現在の連続数を0へ戻し、誤打を含む語の完成では増やさない。無誤打完成で1増やし、便内最大を更新する。通常の実績に用いる過去の自己最長は、適格な完走時に更新する。練習の自己最長は練習の確定完成ごとに更新し、通常の記録と混ぜない。一時停止は連続数を切らない。未完成の語を飛ばした場合と新しい練習セッションの開始時は現在の連続数を0に戻す。完成後に次の語へ進むことや同じ語を繰り返すことでは切らない。C04・C05・C06・H02は便内最大を条件にするため、到達後の誤打でも達成済みの長さを失わない。ただし通常資格は完走時に必要となる。

### 11.4 成長比較と練習資格

D04・D05の比較元は、実績導入後に確定した通常の便で、完成語数10以上かつ比較キーが一致するものから取る。得点の最高と速度の最高を別々に保持し、本編開始前の値を固定する。今回も10語以上完成した場合にだけ更新経路を評価する。比較元がなければ更新とは扱わず、D04の1000点、D05の基準打鍵毎分180という代替条件を示す。代替条件は比較元を必要としない。

F06用の練習資格は、READYへ入る時に、その時点で練習の無誤打完成を累計3回以上満たした語IDを固定する。本編開始後に他の練習で増えた資格を同じ便へ追加しない。F03のタグは1語に複数あれば該当する全種類へ登録できる。F04では語ごとの3回資格を満たした異なるID数を数える。

### 11.5 数値の判定と仮達成

正確率の閾値は、正解数をc、誤打数をm、閾値をpとし、100×cがp×(c+m)以上かで判定する。分母0では達成しない。速度は基準長合計Lに対してL×60000÷90000を使い、表示用の丸め値で判定しない。通常結果の指標は小数1桁の四捨五入、実績の割合進捗は小数1桁切り捨てとし、閾値未満を達成値に見せない。

通常の便内における配達、順序、最大連続数などは、成立済みの事実として保持できる。ただし表示は「達成記録あり。スキップせず完走で解除」とし、未完走の状態を解除済みにしない。正確率を含む条件は後の誤打で変わるため、「現在は条件内。終了時に判定」として最新値を使う。

スキップで通常資格を失った場合、通常の目標を今回対象外へ更新する。H05はガイドを一度でも表示したら同様に対象外とする。これらの対象外表示は既に解除した実績を取り消す意味にしない。音、文字拡大、動き軽減、一時停止、条件公開で資格を失わせない。

### 11.6 解除と報酬と未読

解除は実績IDの集合への追加とする。同じIDは条件版が変わっても重複解除しない。切手と称号は解除と同じ更新で所有物へ加え、受取ボタンや手帳閲覧を要求しない。称号の装着は本人が選び、最新の称号へ自動切替しない。

報酬の閾値は、各系統3件の絵葉書・装飾、6件の箔押し台紙、全体8・16・24・36・48・60・72件の節目とする。解除総数は72個の実績IDだけから数え、節目の報酬や記念切手を実績数へ再加算しない。1回の同時解除で複数閾値を越えたら、その全報酬を同じ処理で付与する。街の表示更新は結果またはHOMEで行い、本編の入力配置を変えない。

未読は解除と別に持つ。通知を抑制した場合や、結果演出を見ず再挑戦した場合も、解除と報酬の所有は保持する。既読への変更は手帳の閲覧操作として処理し、進捗・得点・所有物を変えない。全72件解除後は未解除のおすすめを空にし、新しい階層や日課を自動追加しない。

全体48枚の「48枚の記念台紙」は解除総数48以上で付与し、A〜Hの48件すべてを満たす「第1集完成」は別の報酬キーで付与する。追加実績を含む48枚だけで第1集完成とはしない。旧版で取得済みの第1集報酬は維持する。実績報酬に収益や輸送力を付けず、建築された街の機能は経済状態だけで決まる。

条件調整で過去の解除を取り消さない。定義の版が変わった時は、新たな未解除判定だけへ新条件を適用する。現在保存している確定集計で評価できる条件は再評価できるが、存在しない過去の事実を推定して補わない。実績の全削除を行った場合だけ、明示的に新しい計測世代として始め直す。

## 12 表示と音声の実装条件

入力用の実input要素と、見た目のローマ字ガイドを分ける。ゲーム内の文字と操作部品はDOMで描画し、装飾のみSVGまたはCanvasに置く。入力要素にはラベル、フォーカス表示、読み上げ用の説明を持たせる。

### 12.1 レイアウトと文字

各画面の具体的な配置と表示状態は[画面設計書](screen_design.md)と対応付ける。以下の文字サイズ、必要幅、状態表示の条件を画面全体へ適用する。

日本語本文は標準32 CSS px以上、読み22px以上、ローマ字24px以上、補助文16px以上を初期値とする。文字サイズは100/125/150%を選べる。横幅960 CSS px以上では1画面に主要情報を収める。768〜959pxでは背景を縮め、文字サイズを下げずに配置を変える。768px未満では90秒の本編の開始前に必要な表示幅を案内し、縮小で無理に入力させない。物理キーボードを用いる練習と閲覧は縦配置で使えるようにする。

ガイドは等幅フォントで最大3行を確保し、表示文・読みも最大2行分を予約する。入力済み文字は色と下線を併用し、次の文字は枠を付ける。未入力文字を薄すぎる色にしない。ガイドをOFFにしても日本語と読みは残し、誤打後の任意ヘルプでガイドを出せる。

### 12.2 実績の通知と手帳

ライブ通知は語の境目でのみ開始し、固定領域に最大1.2秒、同時に1件だけ出す。前回の開始から10秒未満に成立した解除は、個別通知の列へ積まず、件数と実績IDを結果表示用の集合へまとめる。表示中の新規解除も記録へ残すが、通知時間を延長しない。ライブ短音は既定で出さず、入力・語完成・配達の音を優先する。

通常の便の解除はRoundFinishedの確定後に結果へ表示する。新しい切手は最大3枚、そのほかを件数へまとめ、再挑戦操作を演出の完了待ちにしない。目標表示は1件、解除判定は全72件である。通知を「結果のみ」にしても進捗・解除・報酬を同じように処理する。

PRACTICEを終了してHOMEへ戻る場合は、今回の練習で得た切手の件数を1行で表示し、手帳の新着履歴へ接続する。専用RESULTや表示待ちは追加しない。本編へ直接進む場合は未表示の実績ID集合を次のHOMEまたはRESULTまで引き継ぎ、「練習で獲得」と出所を区別して集約する。同じIDを重複表示用に加算せず、所有と未読は第11.6節の規則を維持する。

手帳・図鑑はDOMで構成し、条件、進捗、遊び方、報酬、未読を文字でも示す。隠し条件の公開フラグは表示だけに使う。手帳を閉じても停止中の時計を自動で進めない。ライブ読み上げを1打ごとに重ねず、解除と結果をまとめる。

### 12.3 演出と音声

手応えは、打鍵、語の完成、配達の3段階で大きくする。入力ごとの反応は軽く、まとめて届ける時だけ大きな解放感を出す。得点や荷物の状態変更は演出の終了を待たずに完了する。

| 契機 | 見た目 | 音と時間の初期値 |
| --- | --- | --- |
| 正しい打鍵 | 次の描画で文字を確定 | 小さな短音。残響80ms以下 |
| 語の完成 | 誤打の有無にかかわらず完成点と小さな灯りを示す。無誤打なら荷物も1個増える | 軽い完成音。150ms |
| 配達1〜2個 | 荷物が街へ飛び、灯りが増える | 配達音。250ms |
| 配達3〜4個 | 少し大きい軌跡と住人の反応 | 上昇する短い和音。350ms |
| 配達5個 | 荷物の姿勢を50ms留めて一斉に送る | 短い祝福音。全体450ms |
| 誤打 | 次文字の枠を短く変え、損失ボーナスを控えめに示す | 低音量の通知音。100ms |

50msの「止め」は荷物の絵だけに使う。タイマー、入力受付、ローマ字の更新、次の語は停止させない。文字カード、カメラ、画面全体は揺らさない。全画面の白フラッシュは使わない。動きの軽減をONにした場合、移動や拡縮を簡潔な静止表示に置き換えるが、点数とルールは同一にする。

音量はBGM、効果音、全体を別々に設定でき、初期値は全体50%、効果音70%、BGM25%。最初のユーザー操作で音声を開始し、再生に失敗してもゲームを止めない。重要度は配達完了＞語の完成＞誤打通知＞打鍵音＞BGM。同時発音数を8に制限し、過密時は古い打鍵音から間引く。音だけで成功・失敗・残り時間を伝えない。

音声はユーザーの開始操作でAudioContextの開始または再開を試みる。Web Audio仕様の`A user agent may disallow this initial transition`を前提に、音が利用可能になるまでゲームを待たせない。失敗時は消音で進め、音量設定の近くに再有効化操作を置く。[技5]

## 13 調整可能な値

変える可能性のある値は、【日本語名】と機械識別子を対応付けた設定に置く。仕様の関係式は【語の完成点】＝【基準1打点】×基準長のように記述し、値の欄を○で表す場合の○は、この表の初期値を指す。未決定値を実装へ残す意味ではない。

| パラメーター | 識別子 | 初期値 | 調整範囲 |
| --- | --- | --- | --- |
| 【制限時間】 | roundDurationMs | 90000ms | 試作で60〜120秒。公開版の全コースで統一 |
| 【基準1打点】 | pointPerCanonicalKey | 10点 | 表示尺度。得点規則の版を変更 |
| 【最大荷物数】 | maxCargo | 5個 | 3〜5個 |
| 【荷物数係数】 | cargoRateNumerators | 1,2,3,4,5 分母5 | 単調増加を維持。確定点には掛けない |
| 【配達の静止時間】 | deliveryHoldMs | 50ms | 0〜80ms。絵だけに適用 |
| 【配達演出時間】 | deliveryFxMs | 250,350,450ms | 150〜500ms。入力は待たない |
| 【再挑戦UI待ち】 | retryUiBudgetMs | 300ms以下 | 人為的な待ちを追加しない |
| 【効果音同時数】 | maxSoundVoices | 8 | 4〜12 |

最大荷物数を調整する場合は、その数で係数1.0となる対応表も同時に変更し、ボーナス表示、チュートリアル、試験期待値を一括検証する。初版の正式ルールは第3節の5個・分母5で固定する。

開発用画面では、任意の語、荷物数、残り時間、IME停止、得点イベント、乱数seedを再現できるようにする。数値変更は停止中に適用し、比較用セッションを再開始する。進行中の採点条件をこっそり変更しない。開発用操作を使った結果は通常記録に保存しない。

## 14 対応環境と品質目標

対象はWindows 11のChrome・Edge・Firefox、macOSのSafari・Chromeとする。公開時点の安定版と1世代前を試験対象とし、実行したOS・ブラウザー・IME・配列の版を試験記録へ残す。表に含むことを、現時点で動作確認したという意味にはしない。

| Windows 別配列 | US配列、Google日本語入力のON/OFF、Chrome |

初期の品質目標は、4論理コア・メモリー8GB・内蔵GPU相当の検証用PCで、通常表示時60fpsを目指し、キー処理から表示更新までP95で50ms以下とする。キー処理単体はP95で5ms以下、アプリに起因する50ms以上の連続タスクを本編中に出さない。測定時の実機名・OS・ブラウザー・画面倍率を併記する。性能不足時は粒子を減らし、文字と判定を優先する。

初期転送量は圧縮後3MB以内、低速条件として10Mbps・往復遅延100ms・キャッシュなしで、開始操作可能までP95で3秒以内を目標にする。フォントはシステム日本語フォントを優先し、外部フォントの完了待ちを開始条件にしない。音楽が遅れても必要な文字と入力が準備できたら開始可能にする。題材データが利用不能の場合だけは開始させず、再読込操作と原因を示す。

手帳の全72件、図鑑の全960語、同時解除、保存処理を含めて性能を測定する。実績の計算と保存が入力遅延の原因となる場合は、入力処理から集計・永続化を分け、表示量を減らす。解除条件の取りこぼしで性能目標を満たしたことにしない。

通常の本文・入力文字のコントラスト比は4.5:1以上を基準とし、正誤・荷物・配達可能状態を色だけで表現しない。フォーカスを見失わない表示、キーボードだけで完結するメニュー、動きの軽減設定、練習中の手動読み上げを提供する。自動読み上げは1打ごとに行わず、完了と状態変更をまとめる。

### 15.3 IMEと確定境界の実機試験

WindowsのMicrosoft IMEとGoogle日本語入力、macOSの日本語入力について、第14節の対象ブラウザー・配列で試験する。各試験ではイベントの種類、key、code、inputType、data、isComposing、操作ID、仮反映と確定事実の発行位置を記録する。個人の自由入力を収集せず、固定の試験語だけを使う。

| 試験場面 | 合格条件 |
| --- | --- |
| 最初のaをIME ON/OFFそれぞれで確認 | 確認用入力は得点・実績へ入らない。半角入力だけが開始条件になる |
| 語の最終キーで合成開始がkeydownより後に観測される | 仮表示を戻し、語完成と切手を確定しない |
| IME終了付近でisComposingがfalseになる | 境界の確認だけで配達・語完成を誤確定しない |
| Enterで変換を確定 | そのEnterを手動配達や再開へ転用しない |
| 半角a確認後に元の語へ戻る | 確定済み文字・荷物・点数・実績は維持し、確認用aを混ぜない |

シミュレーション上のイベント順だけで実機合格としない。上の境界で誤解除や正解入力の欠落が出る環境は、イベント対応付けを修正してから公開対象とする。

## 16 街の経済・物流・再出発

街はタイピングで作った資材を実時間で運び、開発計画を完成させ、店舗の営業収益を設備へ再投資する。数値の正本は[economy_config.json](../data/economy_config.json)、式と境界を再現する標準Pythonの参照モデルは[economy_model.py](../tools/economy_model.py)、検査結果と仮定別の進み方は[経済バランス検証書](economy_balance_report.md)に置く。この参照モデルはブラウザー本体の実装・実機試験を代替しない。参照APIの`mode`は検算場面のラベルで、`normal`は通常のMAIN、`skip`は救済ありのMAIN、`practice`と`review`はPRACTICE、`intro`はTUTORIALに対応する。GameSessionの3モードを5モードへ増やす指定ではない。

### 16.1 資源、保存精度、入力からの生成

資源はコイン・資材・設計図の3種とする。コインと資材は1単位を1,000,000 microで持つ符号なし整数、設計図と設備所有数は整数で保存する。JavaScript実装では計算にBigIntを用い、JSON保存時はmicro値を10進文字列へ変換する。小数の丸めは表示のみに使い、閾値判定・支出・配分に表示値を再利用しない。価格の指数計算も整数の分子・分母から切り上げ、浮動小数点の誤差で価格が変わらないようにする。

タイピング得点は第3章から変更しない。Lを語の基準長、Pを確定したおまとめボーナスとすると、基本資材はL、追加資材はP÷10。これに荷づくり倍率と荷札研究倍率を掛けて届け先の輸送待ちへ積む。TUTORIAL、PRACTICE、MAINの確定完成を対象とし、誤打を含んで完成した語にも基本資材を与える。入力確認のa、途中までの語、実績の閲覧、放置時間から新しい資材を作らない。

| 事実 | 得点 | 新しく作る資材 |
| --- | --- | --- |
| WordCompleted | 10L | L×荷づくり倍率×荷札研究倍率 |
| DeliveryCommitted（manual/full/deadline/skip） | P | (P÷10)×同じ倍率 |
| 誤打で未配達ボーナスを失う | 確定点は維持 | 既に作った基本資材は維持。未確定の追加資材は作らない |
| 途中終了 | 完走記録にしない | 確定完成から作った資材は残る。未配達分の追加資材は作らない |

届け先、cityId、資材倍率はMAINのREADY、TUTORIAL/PRACTICEの開始時に固定する。MAINの準備・プレイ・停止中は投資操作を禁止し、練習中は終了してから投資へ移る。輸送速度と店舗収益は購入時から変わるが、すでに作った資材の量は再計算しない。

例としてL=3、荷づくりLv1、研究0なら3.75資材を作る。0.75を切り捨てない。荷物3個の完成点合計が230ならボーナス138点、追加資材13.8。荷づくりLv10ならこの追加分は96.6になる。画面は少量の増加を小数1桁または詳細表示で示し、切り捨てによる「強化したのに増えない」という表示を避ける。

### 16.2 地区、開通、開発計画

輸送網は中央集配所と6地区を結ぶ固定路線である。地区選択、路線開通、配送班増員、鉄道化は操作できるが、自由な線路敷設、ダイヤ編集、車両同士の衝突は扱わない。各開通路線は独立に同時輸送する。

| districtId | 表示名 | 費用係数f | 開通に必要な現在の街の段階合計 | 開通コイン | 店舗1軒の基礎収益/秒 |
| --- | --- | ---: | ---: | ---: | ---: |
| residential | 住宅地 | 1 | 0 | 0 | 0.1 |
| market | 商店街 | 2 | 2 | 150 | 0.2 |
| workshop | 工房街 | 4 | 4 | 600 | 0.4 |
| park | 公園通り | 8 | 7 | 2400 | 0.8 |
| station | 駅前 | 16 | 11 | 9600 | 1.6 |
| harbor | 港町 | 32 | 16 | 38400 | 3.2 |

初期状態はコイン0、資材0、住宅地の路線だけ開通、配送班1、地区段階0、店舗0。住宅地の段階1計画を費用0で開始しておく。以後の計画は自動では始めず、プレイヤーが次の投資先を選ぶ。

| 到達段階 | 今回必要な資材の基礎値 | 今回必要なコインの基礎値 | その段階での店舗上限 |
| --- | ---: | ---: | ---: |
| 1 | 30 | 0 | 5 |
| 2 | 150 | 100 | 10 |
| 3 | 600 | 600 | 20 |
| 4 | 2400 | 3000 | 35 |
| 5 | 9000 | 15000 | 50 |

計画の資材・コインは表の値×地区係数f。各行は直前の段階から上げるための追加費用であり、累計値ではない。地区の段階を飛ばせない。開始時にコインを前払いし、自由在庫を必要量まで予約資材へ移す。その後の到着資材も必要量まで予約へ回す。必要量に到達した時刻に即時完成し、追加の待ち時間を置かない。段階1の完成時だけ、その地区へ無料店舗1軒を一度付与する。

計画は無料で一時停止・再開できる。一時停止しても前払いコインと予約資材は保持し、それ以後の到着は自由在庫へ入れる。再開時は自由在庫を必要量まで再び取り込む。計画の取り消し・払い戻しは初版では行わない。画面では予約分、自由在庫、輸送待ちを混ぜずに表示する。

鉄道化に使う資材は自由在庫だけである。建築へ予約した資材を黙って消費しない。「計画を一時停止し、届く資材を在庫へ回す」という操作経路を設備画面から示す。全6地区を段階5にする計画費用の合計は767,340資材、全鉄道化の資材費は31,500、合計798,840資材である。通常の配送は資材を消費しない。

### 16.3 輸送、入金、設備

資材は生成時に届け先の輸送待ちへ入り、輸送能力に応じて少しずつ到着する。到着時に基礎2コイン/資材を一度だけ入金し、計画が稼働中なら予約へ、残りは自由在庫へ配分する。倉庫容量制限・廃棄・入力停止は設けない。予約や自由在庫の移動では再入金しない。

nを現在のレベルまたは所有数とし、m(n)を10・25・50のうちn以下の節目の数とする。

| 設備 | 次の1つの価格 | 効果・上限 |
| --- | --- | --- |
| 荷づくり | ceil(50×1.18^n) | 倍率=(1+0.25n)×2^m(n)。Lv0〜50 |
| 配送班 | ceil(40×f×1.15^(n−1)) | 基礎能力=4n×2^m(n)資材/秒。各開通路線1〜50班 |
| 店舗 | ceil(25×f×1.16^n) | 基礎収益×n×2^(地区段階−1)×2^m(n)コイン/秒。上限は段階表 |
| 鉄道化 | 3000fコインと500f自由資材 | その路線の能力×4。地区段階3以上かつ配送班10以上で1回だけ購入 |

荷づくり倍率はLv0=1、Lv10=7、Lv25=29、Lv50=108。10・25・50の節目では増加後の基礎値全体に倍増を適用する。店舗の営業に追加の資材、維持費、購入回数制限は必要ない。設備によってタイピング得点、正確率、基準打鍵/分、90秒の制限は変えない。

「1」「10」「買えるだけ」は実際の購入可能数を見積もる。残高と上限から順に次の価格を計算し、購入数量、合計費用、購入後の所有数、購入前後の倍率を表示する。「10」を選んでも上限や残高で3しか買えない場合は「3購入」と表示する。確認後の同一トランザクションで価格と残高を再評価し、古い見積もりで残高を負にしない。残高不足では購入しない。無料店舗付与は有料購入実績へ加算しない。

配送設備には現在の輸送待ちと、追加投入がない場合にその待ちを運び切る時間の購入前後を併記する。待ちが0なら「現在は輸送待ちなし」と示す。最大能力の倍増と、実際に到着する資材の倍増を同一と説明しない。配送量が供給不足の場合も資材を補って作らない。

### 16.4 地区間の連携

| 連携 | 条件 | 費用 | 効果 |
| --- | --- | ---: | --- |
| 共同配送 | 住宅地・商店街が段階2以上 | 1000コイン | 到着手数料2→3コイン/資材 |
| 仕分け連携 | 工房街・駅前が段階2以上 | 12000コイン | 全路線の輸送能力×2 |
| 観光便 | 公園通り・港町が段階3以上 | 100000コイン | 全店舗の営業収益×2 |

連携は現在の街で各1回購入できる。条件と効果を購入前から表示し、購入時までの経過は旧倍率、購入後だけ新倍率で計算する。研究倍率は同じ能力へ別に乗算する。

### 16.5 2つの時計と放置中の処理

本編の90秒は有効プレイ時間、街は実経過時間で進む。一時停止、IME確認、結果の閲覧中にも既存の輸送待ちと店舗収益は進む。ゲームを開いていない間は、保存した基準時刻から最大8時間を一度だけ反映する。新しい語、基本資材、ボーナス、正解打鍵、完走、練習成功を放置から生成しない。

オンラインの連続処理は単調時計の差を使う。復帰時は`max(0, currentWallTime−savedWallTime)`を上限28,800,000msに切り詰め、処理済み基準時刻を保存値と現在値の大きい方へ進める。処理結果と基準時刻は同じ保存トランザクションで確定する。時計が逆行した場合は0msとして扱い、基準時刻を巻き戻さず、残高や進捗を減算しない。再表示・再読み込みで同じ時間を重複入金しない。これはローカル一人用の利便性の契約であり、端末時計変更に対する不正防止を保証するものではない。

経過時間は輸送待ちが空になる時刻、計画が完成する時刻、購入等の外部イベント時刻で分割する。各区間を旧状態で進め、境界で到着・建築完成を適用してから新しい収益で次へ進む。内部時刻は整数ms、境界は条件へ最初に到達するmsへ切り上げる。輸送は待ち量を超えず、端数計算の残りも持って分割回数による差を防ぐ。

例として初期の住宅地へ30資材が輸送待ちとしてあり、配送班1で60秒進めると、7.5秒で段階1が完成する。到着手数料は60コイン、無料店舗の収益は残り52.5秒×0.1=5.25コインで、合計65.25コインになる。初めの7.5秒分の店舗収益を遡って与えない。

放置の反映は自動で行い、受取ボタン、広告、日付条件を挟まない。帰還時は経過の適用時間、到着資材、営業収益、完成した計画を一枚にまとめ、閉じる前から資源と実績は確定済みとする。

### 16.6 新しい街と永続研究

再出発は任意とする。条件は現在の街の6地区がすべて段階3以上、かつ現在の街の累積到着資材が100,000以上。得る設計図は`3×floor(sqrt(現在の街の累積到着資材÷100000))`。整数平方根を用い、100,000/400,000/900,000到着で3/6/9枚となる。次の枚数境界と必要な残り資材を操作前に表示する。

確認画面では、消えるもの、残るもの、今回得る設計図、その設計図で選べる研究を並べる。初回3枚は3系統を1段ずつ上げる使い方と、1系統を2段上げる使い方ができる。設計図を使うまで勝手に強化先を決めない。

| 研究 | 適用対象 | ランク・費用 | 倍率 |
| --- | --- | --- | --- |
| 荷札設計 | 生成する基本・追加資材 | 0〜5、次ランク費用1/2/3/4/5枚 | (4+ランク)÷4 |
| 物流設計 | 全路線の輸送能力 | 同上 | 同上 |
| 商い設計 | 全店舗の営業収益 | 同上 | 同上 |

荷札設計ランク1なら最初の建築に必要な基礎資材は30÷1.25=24相当で、研究なしより20%少ない。これは資材量の比較であり、入力の速さ・待ち方を含む実時間の20%短縮を実測したという意味ではない。

HOME/RESULTで進行中セッションを閉じてから一つのトランザクションで再出発する。旧cityIdの計画・資源・設備・輸送待ち・連携を消し、新cityIdで初期状態を作り、設計図を一度だけ加算する。研究、未使用の設計図、実績、切手、称号、図鑑、練習資格、自己記録、設定、累積到着資材は保持する。住宅地等の地区集合を条件とする実績は現在のcityId内で判定し、複数の街の段階を合成しない。旧cityId宛ての遅延イベントは新しい街へ適用しない。

景観は川沿い・海辺・高原から選べる。景観による経済差はなく、特定景観を選ばないと実績を取れない条件も設けない。

### 16.7 画面へ渡す値と履歴

結果の集計では「今回作った資材」「この便の間に到着した資材」「終了時点の輸送待ち」を別に持つ。生成量は当該sessionIdの生成事実から、到着量は開始・終了間の街の累積差分から求める。到着には以前の便の輸送待ちも含み得る。輸送待ちは当該便だけの残りと誤解させず、届け先の総量として表示する。

店舗収益はセッションの有効90秒ではなく、開始から終了までの街の実経過に対応する。途中で長く停止した回の収益を「90秒で稼いだ額」と表示しない。資材と営業の詳細は結果の街欄で開き、通常の得点・正確率・速度との意味を混ぜない。

街の完成、到着、設備購入、研究がI/J/K系統の事実を作り、960語の収集はL系統の確定完成で判定する。経済イベントが打鍵や完走を偽造しない。通知は確定後に表示し、本編中の大きな建築演出は結果/HOMEへ送る。実績が24枚に達したことだけでは街を完成させない。

### 16.8 原子更新、複数タブ、移行

資材生成は`(sessionId,factSequence)`、経済操作は`(cityId,economyEventId)`で一意にする。イベント受信時にはまず旧状態でその時刻まで進め、到着・計画完成を確定してから購入・生成を適用する。完成による無料店舗、到着入金、設備消費、解除、報酬、処理済み位置、時計の基準を同じreadwriteトランザクションに含める。輸送待ち・自由在庫・予約・コインは常に非負、同一cityId内の生成量の累積は、その都市の到着量と輸送待ちの合計へ整合する。再出発で破棄した旧都市の輸送待ちを、現在の街の待ちと生涯値の式へ混ぜない。

操作できるタブは1つに限定する。保存のmetadataにownerTabIdとwriteEpochを持ち、同一トランザクション内で所有権を取得する。別タブは閲覧状態と「ここで続ける」を示す。明示的な引継ぎでepochを更新し、前タブの非同期保存と購入は古いepochとして拒否する。所有権喪失を検出した本編はPAUSEDへ移る。復帰計算を2タブが同時に要求しても、最初のトランザクションが更新した基準時刻から後続を評価する。IDBを使えない場合はそのページ限りのメモリー運用となり、複数ページ間の同期を保証しないことを表示する。

保存失敗時には今回のみの状態を表示し、未保存イベントを同じIDで保持する。再試行は保存済みの基準revisionとepochを検査して適用し、同じイベントや時間を再加算しない。別タブが新しい状態を確定していたら古い全体スナップショットで上書きしない。再読み込み時に元へ戻る可能性を隠さない。

保存形式の版は4とし、旧版のIDBからは設定・記録・A〜H実績・報酬・図鑑・練習資格を保ったまま、資源0の初期の街を追加する。過去得点からコインや資材を遡及発行しない。旧240語は全960語と初版集合の両方へ同じIDで所属させ、E04は旧集合、L系統は新集合を判定する。旧48枚報酬と新しい全体48枚台紙は別キーに移す。移行済み印と新状態を同じトランザクションで確定し、失敗時に旧状態を先に削除しない。

## 17 実装の完了条件

公開前には、入力の全基本経路、誤打復帰、荷物と得点、90秒の終了境界、IME中断、停止復帰、練習、保存不能時の継続を確認する。試験は純粋な判定ロジックの自動試験、DOMと状態を接続する試験、対象環境での物理キーボード・IME試験に分ける。

受入試験の全件成功、対象環境の確認、進行不能・誤採点・保存失敗によるプレイ停止の解消を技術上の公開条件とする。実績のイベント、保存、重複防止、通知に加え、街の生成・輸送・計画・購入・放置・再出発と複数タブについても本書の対応試験を公開条件に加える。初見観察と実際の遊び心地の合格基準は[ゲーム体験仕様書](game_experience.md#11-体験の合格条件)で管理する。

開発用の状態注入や数値変更を使ったセッションは通常記録へ加えない。性能を測定する時は、実機名、OS、ブラウザー、IME、配列、画面倍率、測定方法、試行数を記録する。仕様例の参照モデルが一致することと、ブラウザーで実際に入力できることは別に判定する。

## 19 美術資材とゲーム状態の接続

[資材の実装仕様](resource_implementation.md)で、ゲーム項目IDから資材ID、表示状態、描画順、出力形式までの契約を定める。[資材マスター](../data/visual_resource_manifest.json)は241点の画像・SVGと音源7点の台帳であり、描画状態の組み合わせや倍率を新規原画へ加算しない。

実績72件、地区36段階、設備の全レベルは別々のマスターに保持する。名称・条件・価格・効果と画像の都合を切り離し、未解除や購入不可の理由はDOMへ表示する。選択中、目標固定、未読、装着中は独立の表示である。原画の生成や演出の完了を、実績・資材・購入の確定条件にしない。

資材検査器は全件の参照、価格644セル、外観帯、研究18状態、原画と書き出し数、正本のハッシュを照合する。検査結果は[資材検証報告](resource_validation_report.md)に記録し、原画の実寸検収や実機でのIME試験とは分ける。
